# 4. Enterprise AI — What to Talk About

Do not turn the conversation into a list of AI tools.

Use this sequence:

**Business outcome → Use case → Data/context → AI pattern → Controls → Operations → Adoption**

## Business value

Think about:

- Revenue
- Cost
- Cycle time
- Risk
- Customer/employee experience

Ask:

> “What decision or workflow changes because of AI?”

## Key Oracle / AI concepts

### OCI Generative AI

Managed access to large language models through cloud services and APIs.

### RAG

Retrieve relevant enterprise context first, then ground the model's response in that context.

### AI Vector Search

Store and query embeddings for semantic retrieval close to enterprise data.

### OCI Generative AI Agents

Agent patterns involving knowledge, tools, sessions, and guardrails.

### Enterprise AI risks

Be ready to discuss:

- Data quality
- Access control
- Privacy
- Intellectual property
- Prompt injection
- Hallucination
- Bias
- Integration
- Latency
- Resilience
- Model choice
- Evaluation
- Observability
- Cost
- Adoption
- Human accountability

### Your strongest differentiator

> “My identity-platform background makes me attentive to least privilege, authorization, auditability, and secure integration — the same controls that become critical when AI reaches enterprise data and actions.”

### Three phrases to remember

> **“Start with the decision or workflow, not the model.”**

> **“Grounding improves relevance; it does not eliminate the need for evaluation and controls.”**

> **“A pilot proves value and operating feasibility, not just technical possibility.”**

# 5. Strategy Framework

When given an ambiguous AI strategy question, use:

## Objective → Use Cases → Foundation → Target State → Roadmap → Scale

### 1. Frame the business objective

Ask:

- Which metric must move?
- For whom?
- By when?
- What decision/workflow is changing?
- What constraints exist?

### 2. Prioritize use cases

Consider:

- Business value
- Feasibility
- Risk
- Data readiness
- Time to impact
- Reusability

Do not create a “demo parade.”

### 3. Assess the foundation

Review:

- Data
- Integration
- Cloud
- Security
- Identity
- Model options
- Skills
- Existing operating constraints

### 4. Define target state + guardrails

Cover:

- Architecture
- Access boundaries
- Evaluation
- Human oversight
- Vendor strategy
- Reusable platform capabilities

### 5. Roadmap

Think:

- **0–90 days:** bounded pilots
- **3–6 months:** platform capabilities
- **6–18 months:** scale

Identify:

- Owners
- Dependencies
- Investment
- Change impacts

### 6. Prove, measure, scale — or stop

Define before the pilot:

- Baseline
- Quality gates
- Adoption measures
- Unit economics
- Risk thresholds
- Scale/stop decision

### Strong case statement

> “I would separate the decision into value, feasibility, and responsible scale. First, define the business metric. Second, prioritize use cases. Third, assess data and platform readiness. Then design the target state and controls, run a bounded pilot, and scale only against pre-agreed evidence.”

### What makes this strategy?

**Choices:** What not to fund.

**Economics:** Value, investment, sequencing, unit cost.

**Change:** Operating model, adoption, governance, accountability.

# 6. Mini Case: Enterprise AI Assistant

### Scenario

A global company wants an AI assistant over internal policy and support documents.

Leaders want a fast launch.

Security/compliance teams are concerned.

## Clarify first

Ask:

1. Who are the users?
2. What are the highest-value tasks?
3. Which documents/systems are authoritative?
4. What data classifications and regions are involved?
5. Does the assistant only answer, or also take actions?
6. What is the current baseline — search time, ticket volume, error rate?

## Working hypothesis

Use a **bounded RAG assistant** to reduce time spent finding approved information without giving the model unrestricted access or autonomous decision rights.
